# 커플앱 Android/iOS 통합 개발 PRD

> **문서 버전:** 1.0 · **작성일:** 2026-11-07  · 현행화:** 2026-11-07  
> **대상:** React Native + Expo · Android / iOS · Codex 단계별 구현  
> **제품 상태:** 기존 Android 앱은 없다. 제공된 Android 화면 스크린샷을 시각적 참고 자료로 사용해 React Native + Expo 앱을 신규 구현 중  
> **문서 성격:** 화면으로 확인된 사실(F), 구현 제안(P), 확인 필요(TBD)를 구분한 개발 기준서

## 0. 문서 사용법과 구현 원칙

- 이 문서는 업로드된 **8개 Android 화면**을 기준으로 작성했다. 보이지 않는 화면·기능·내부 로직을 이미 존재하는 것으로 단정하지 않는다.
- **F(화면 확인):** 첨부 화면에서 직접 확인되는 UI 또는 동작을 암시하는 요소. **P(구현 제안):** 원활한 작동을 위한 추천 규칙. **TBD(미확정):** 실제 소스·요구사항 확인이 필요한 항목.
- **제공된 Android 화면 스크린샷을 기능·디자인 참고 자료로 사용**한다. 실제 Android 앱은 없으며, 기존 앱 기능 호환이나 기존 데이터 이관은 범위에 포함되지 않는다. 스크린샷만으로 확인할 수 없는 동작은 사용자 요청과 현재 프로젝트 구현을 기준으로 정한다.
- Codex에는 모든 PRD를 매 요청에 붙여 넣지 않는다. `CODEX_TASK.md`에서 **현재 작업 ID 하나만** 지시하고 본 PRD의 해당 절만 확인하게 한다.
- 각 단계는 별도 브랜치 또는 커밋으로 관리한다. 구현 → 최소 관련 검증 → 실제 기기 확인 → 승인 → 다음 단계 순서로 진행한다.
- 기념일·생리 기록·사진은 사적인 정보다. 동기화와 공유 범위는 사용자가 결정하기 전까지 임의로 확장하지 않는다.
- 제공 스크린샷은 UI와 표시 정보 참고 자료이며 기존 실행 앱·소스·저장소를 뜻하지 않는다. 이 프로젝트에는 기존 Android 앱이 없고, 기존 사용자 데이터 이관은 요청 범위에서 제외한다.

## 1. 제품 개요

### 1.1 제품 목표

연인이 함께하는 날짜와 기념일을 확인하고, 월별 달력에서 중요한 날을 관리하며, 생리주기를 기록하고, 데이트 일기·위시리스트·선물 메모를 저장하는 **개인 커플 라이프 기록 앱**을 Android와 iOS에서 일관된 UI/동작으로 제공한다.

### 1.2 해결할 문제

1. 기념일·공휴일·연인 이벤트를 여러 앱에서 확인해야 한다.
2. 커플의 교제 시작일부터 오늘까지 날짜를 즉시 보기 어렵다.
3. 생리일, 예상 주기, 증상 메모를 한곳에 정리하기 어렵다.
4. 데이트 사진과 장소, 아이디어와 선물 메모가 흩어진다.
5. 현재 Android UI를 iOS로 이식할 때 아이콘·이모지·폰트·Safe Area가 다르게 보인다.

### 1.3 성공 지표 및 우선순위

**디자인 자산 정책:** 동일하게 보여야 하는 UI 아이콘은 프로젝트의 기존 벡터 아이콘을 우선 사용한다. OS 기본 이모지는 렌더링 모양이 다르므로 기념일·기분 그림은 프로젝트 보유 이미지 자산 또는 별도 제작 에셋으로 교체한다. 사진/감정 그림 등은 권한 없는 외부 이미지로 자동 대체하지 않는다.

**색상·크기:** 첨부 화면으로부터 시각적 추정은 가능하지만, 정확한 HEX/spacing/font-size는 실제 디자인 파일·기존 스타일 코드에서 추출해야 한다(TBD). 스크린샷 픽셀만으로 디자인 토큰을 확정하지 않는다.

**D-day 계산 규칙 (P):** 교제 시작일을 1일째로 계산한다. 예: 2026-10-08 시작, 2026-10-25는 **D+18**. 다가오는 이벤트는 남은 달력 일수(`D-17` 등)로 표시하고 당일은 `D-DAY`로 표시한다. 100일은 시작일에서 **99일 후**다. 시간·분 단위가 아닌 로컬 `YYYY-MM-DD` 달력 날짜로 계산한다.

**예측 로직 제안(P):** 기초 데이터가 충분하지 않으면 사용자가 설정한 평균 주기·기간을 사용한다. 데이터가 누적되면 직전 기록을 근거로 예측하는 방식으로 점진 확장한다. 실제 생리일은 예측보다 우선하고, 예측치를 사실로 표시하지 않는다. 구체적인 평균 계산 방식, 배란일 추정 산식, 불규칙 주기 처리 기준은 개발 전 별도 검증해야 한다.

**필수 안내문(F):** `예측은 평균값 기반 추정이며 의학적 판단이나 피임 수단으로 쓸 수 없어요.` 이 문구를 계속 표시한다. 앱의 예상 가임기·배란일은 피임이나 임신 가능성 판단을 보장하지 않는다.

**개인정보 보호(P):** 생리·증상·기분 데이터는 민감할 수 있다. 외부 전송·공유를 기본값으로 설정하지 않고, 잠금화면 알림에는 생리 관련 상세 정보를 노출하지 않는다. 연인과의 동기화가 도입되더라도 공유 여부와 범위를 별도로 동의받아야 한다.

## 6. 날짜·시간·공휴일 규칙

1. **달력 날짜는 `YYYY-MM-DD`** 형태의 날짜 전용 값으로 저장한다. `new Date('YYYY-MM-DD')`의 UTC 해석으로 날짜가 밀리는 현상 방지.
2. 교제 시작일 포함 `D+1`, 100일은 시작일 +99일; 미래 이벤트 D-n은 오늘과 이벤트 날짜의 달력 일수 차이.
3. 동시간대 표시 기준은 기본적으로 **기기의 현지 시간대**를 따르며, 대한민국 사용자 대상 UI/공휴일은 `Asia/Seoul`을 고려한다. 타임존을 강제할지(TBD) 결정한다.
4. 앱 재실행·자정 경과·백그라운드 복귀 시 D-day와 알림 예약을 갱신한다.
5. 반복 이벤트는 일회성 날짜와 '다음 발생일'을 구별한다. 연도별 공휴일을 단순히 365일 더해서 계산하지 않는다.
6. 음력·한국 공휴일·대체공휴일은 검증된 원천 데이터를 사용한다. 표기 가능 여부와 반복 로직을 별도로 테스트한다.
7. 기념일과 생리 기록은 달력상 같은 날짜에 겹칠 수 있으며 둘 다 표시할 수 있어야 한다.

## 7. UI/UX 및 접근성 기준

- 다크 배경, 큰 라운드 카드, 핑크 포인트, 하단 5개 탭의 화면 언어를 유지한다.
- 아이콘은 동일한 SVG/벡터 자산을 사용하고 OS 기본 폰트 글리프 의존도를 낮춘다.
- 색상 하나만으로 상태를 전달하지 않고 범례, 레이블 또는 구별되는 모양을 제공한다.
- 탭/스위치/버튼은 최소한 합리적인 터치 영역을 확보하고 버튼 상태를 명확하게 보인다.
- 키보드가 메모 입력칸이나 저장 버튼을 가리지 않도록 한다.
- iOS 홈 인디케이터와 Android 시스템 내비게이션 영역에 콘텐츠가 가리지 않도록 한다.
- 사용자 폰트 확대 시 텍스트가 잘리지 않도록 레이아웃을 검증한다.
- 커플 사진은 문서/예제/오픈 저장소에 자동 포함하거나 외부에 업로드하지 않는다.

## 13. 후속 개선 아이디어 (MVP 이후, 현재 범위 아님)

1. 100·200·300일과 1·2주년 자동 마일스톤 타임라인.
2. 기념일 전 준비 체크리스트(예약·선물·메시지).
3. 데이트 기록의 지도/장소 타임라인(위치 권한 없이 텍스트부터).
4. 장소·음식 취향 태그를 이용한 데이트 후보 추천.
5. 위시리스트 항목을 기념일과 연결하되 강제 공유하지 않기.
6. 선물 구매 여부·예산 메모 및 숨김 옵션.
7. 월말 커플 추억 회고 카드(사진 수·데이트 횟수).
8. 여행 일정과 기념일 충돌을 미리 알려주는 충돌 보기.
9. 이벤트별 알림 묶음·조용한 시간 설정.
10. 생리 기록 비공개 모드와 부분 공유 동의.
11. 데이터 내보내기(JSON/사진 백업)와 복원 검증.
12. 위젯/잠금화면 카드의 개인정보 노출 수준 선택.

> 위 아이디어는 참고 스크린샷에 명시적으로 보이지 않는 신규 기능일 수 있다. 사용자의 명시적 승인 없이 PRD의 P0/P1 작업에 끼워 넣지 않는다.

## 14. 변경 관리 및 Codex 협업 규칙

- `PRD.md`는 제품 요구사항의 단일 기준이다. 세부 작업은 `CODEX_TASK.md`의 현재 티켓을 사용한다.
- 매번 PRD 전체를 요약하거나 프로젝트 전체를 재분석하지 않는다.
- Codex는 작업 범위·변경 파일·실행 검증·미검증 항목을 5~8줄 안팎으로 보고한다.
- 기능 동작 변경이 발생하면 관련 테스트를 갱신하고 해당 요구사항 ID를 연결한다.
- 스크린샷에 없는 동작은 이미 존재한다고 가정하지 않는다. 요구가 불명확하면 실제 프로젝트 상태와 사용자 승인을 기준으로 정하고, 승인된 범위만 구현한다.
- 각 구현 단계 후 사용자 실기기 확인을 거쳐 완료/보류/수정으로 표시한다.
