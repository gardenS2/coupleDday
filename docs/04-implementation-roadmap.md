## 권고 순서와 완료 기준

| 단계 | 화면·기능 | 위험도 | 완료 기준 |
|---|---|---|---|
| 0 자료·환경 | 원본/APK 확보, 저장/백업 확인, 위젯 기술 게이트 | 높음 | 원본 스택 확인 또는 재작성 합의; SDK 버전 고정; 양 OS 위젯 추가 여부를 실측; 이미지 Git 제외 검증 |
| 1 인증·커플 연결 | 초기 온보딩·초대·설정 프로필, 5탭 빈 화면 | 높음 | A/B 가입·연결, C 거부, 동시 초대 정원/중복 가입 테스트; 로그아웃/탈퇴 및 캐시 삭제 |
| 2 일정·기념일 | 홈 → 달력 → 일정 관리·추가 | 중간 | 날짜 전용 저장, 서울 날짜/100일/연말/윤년 테스트, A/B 실시간 동기화·재접속, C 권한 거부; 공휴일 출처 검증 |
| 3 기록·사진 | 일기 → 위시리스트 → 선물 메모 | 높음 | 기본 개인·명시 공유, 작성자 편집, 비공개 파일·EXIF 제거, 공유 철회, 업로드 중단 복구 |
| 4 개인 건강 | 마법 달력 → 당일 기록·과거 기록 → 본인 오버레이 | 매우 높음 | B/C가 직접 API·RPC·Realtime·파일로 우회해도 거부, 로컬 잠금·미리보기 보호, 예측 부족 상태·주의 문구, 삭제·백업 정책 |
| 5 위젯·알림 | D+ → 월 일정 일부 → 개인 설정 | 높음 | 양 OS 실기기 위젯 추가/재부팅/자정·오프라인·앱 종료 검증, 민감 정보 기본 숨김, 알림 취소·재예약·중복 방지 |

PoC가 먼저인 이유는 위젯의 네이티브·서명 위험을 초기에 줄이기 위해서다. 앱의 실제 기능 구현 순서는 요청한 인증→공유 일정→기록→건강→위젯/알림 순서를 따른다. PoC 단일 화면에는 라우터를 추가하지 않았으며 본 앱에서 Expo Router 탭을 도입한다.

## 원본 데이터 백업·이관 평가

현재 소스·APK·DB가 없어 이관 가능 여부는 미확정이다. 원본 개발자에게 프로젝트 전체, 잠금 파일, 빌드 설정, 패키지 ID, 로컬 저장 형식, 공식 내보내기 기능 유무를 요청한다. 서명 키·비밀번호는 채팅/문서에 붙이지 않는다.

원본 앱의 공식 export가 있으면 기기 소유자의 동의로 암호화된 로컬 백업을 만들고 복사본으로 스키마를 조사한다. Android 앱 샌드박스 때문에 APK가 있다고 데이터가 따라오지 않는다. release 앱은 run-as/기본 백업이 막힐 수 있고, 디버그 빌드가 기존 서명과 다르면 기존 데이터 접근을 보장하지 못한다. 삭제·재설치로 조사하지 않는다.

가상 fixture로 날짜·ID·사진 경로·인코딩 변환기를 검증한 다음 사용자별 원본 백업 → dry-run 통계 → 원본/대상 건수·해시 비교 → 사용자 확인 → 별도 이관 작업 순서로 진행한다. 기존 건강 기록의 작성자를 확정할 수 없으면 공유 커플 데이터로 가져오지 않는다. 이관은 멱등 키와 오류 목록을 남기며 rollback용 백업을 유지한다. 이번에는 백업·추출·이관을 실행하지 않았다.

## Android 비공개 설치

PoC는 에뮬레이터 debug 빌드만 대상이다. 지속 사용은 로컬 release APK를 소유자가 관리하는 키로 서명하고 두 사람 중 Android 사용자에게만 안전한 경로로 전달한다. 기기의 해당 설치 출처 허용이 필요하다. 업데이트는 같은 applicationId와 서명 키, 증가한 versionCode를 유지한다. 키 분실 시 기존 앱 업데이트가 어려우므로 암호화 백업을 마련한다. 공개 APK 호스팅/배포 자동화는 아직 하지 않는다. APK에서 공개 client 키가 보일 수 있으므로 데이터 보안은 RLS에 둔다.

## iOS 로컬 테스트와 Ad Hoc

Simulator 테스트에는 실기기 등록이나 개발자 유료 가입이 필요하지 않다. 실제 iPhone에서 Xcode 실행은 연결·기기 신뢰·Developer Mode·서명 팀 설정이 필요하다. 무료 Personal Team은 프로비저닝이 발급 후 7일 만료되어 재빌드/재설치가 필요하고, App ID·기기·설치 앱 수 제한이 있다. 위젯의 App Groups entitlement가 해당 팀에서 가능한지 별도 확인해야 하며 무료 계정으로 이 PoC 전체가 실기기에서 된다고 보장하지 않는다.

[Apple 계정 안내](https://developer.apple.com/help/account/basics/about-your-developer-account)는 Personal Team의 App ID 최대 10개, 기기 최대 3개, 기기당 앱 최대 3개와 7일 제한을 설명한다. [지원 capabilities](https://developer.apple.com/help/account/reference/supported-capabilities-ios)와 [App Groups 설정](https://developer.apple.com/documentation/xcode/configuring-app-groups)을 실기기 단계에서 다시 확인한다.

지속적인 Ad Hoc 설치는 Apple Developer Program 가입, 배포 인증서, 등록된 iPhone UDID를 포함한 프로비저닝, 앱과 위젯 타깃의 동일 App Group 설정이 필요하다. 무기한 서명은 아니므로 프로파일/인증서 만료와 갱신 후 재배포를 관리한다. [Apple 등록 기기 배포 문서](https://developer.apple.com/documentation/xcode/distributing-your-app-to-registered-devices)를 기준으로 등록 한도와 현재 요건을 다시 확인한다. 스토어 공개는 필요하지 않지만 Ad Hoc은 임의 기기에 설치하는 방식이 아니다. 이번 작업에서 결제·계정 로그인·UDID 수집·등록·실기기 서명·배포를 수행하지 않았다.

## 다음 작업 범위 제안

우선 PoC 보고서의 빌드 차단 사유와 실제 홈 화면 검증을 마무리하고, 원본 소스 존재 여부를 확인한다. 이후 **가상 사용자 A/B/C 기반 인증·커플 연결 및 접근 거부 테스트**만 한 작업으로 진행한다. 화면 전체와 사진·건강·알림 서버를 동시에 구현하지 않는다.
