# Codex 첫 번째 작업: 기존 Android 커플앱 분석 + React Native 전환 설계 + 홈 화면 위젯 PoC

너는 React Native/Expo, Android/iOS 네이티브 위젯, Supabase PostgreSQL·RLS에 경험이 많은 모바일 앱 아키텍트이자 시니어 개발자다. 나는 Mac에서 Cursor IDE의 Codex 확장을 사용한다.

## 프로젝트 배경 및 목표
- 기획자가 Claude를 활용해 Android 전용 데모 앱을 만들었고, 현재 데이터는 해당 단말에만 저장된다.
- 데모 APK가 있으며 원본 프로젝트 소스의 존재·기술 스택은 아직 확정되지 않았다. 먼저 작업 디렉터리를 조사해서 실제 자료를 확인해라.
- 목표: iPhone 사용자 1명 + Android 사용자 1명이 비공개로 설치해 함께 쓰는 커플앱.
- 스토어 정식 출시는 계획하지 않는다. Android는 APK 직접 설치, iOS는 우선 로컬 Xcode 실기기 테스트, 지속 사용 시 유료 개발자 계정 기반 Ad Hoc 배포를 검토한다.
- 최종 앱 기술 스택 희망: React Native + Expo + TypeScript + Expo Router, Supabase Auth/PostgreSQL/Storage/Realtime, 필요 시 Edge Functions 또는 DB RPC. 별도 상시 운영 API 서버는 구축하지 않는다.
- 기존 Android 화면의 기능과 UI 톤앤매너를 최대한 보존하고 싶다. 하지만 기존 소스가 Flutter, Kotlin 또는 기타 프레임워크일 수 있으므로 무조건 재사용을 가정하지 말아라.
- 사용자 개인정보와 민감한 건강 기록은 우선 보호한다.

## 반드시 먼저 읽을 참고 화면
프로젝트 폴더의 `docs/references/private/` 아래 8개 이미지가 현재 Android 데모의 실제 화면이다. 이 이미지를 읽어 각 화면을 분석해라. 이 채팅에만 첨부되어 있고 로컬 파일이 없으면 이미지 접근이 불가능하다고 명확히 알려라. 확인되지 않은 화면 동작은 추측이라고 표시해라.

1. `01_home.jpg`: 홈. 커플 이름, 사귄 날짜 기반 D+ 숫자, 다가오는 기념일·공휴일의 D- 목록, 관리 진입.
2. `02_calendar_month.jpg`: 월간 달력, 한국 공휴일·음력 표기, 커플 기념일, 날짜별 상세와 `+ 이 날 추가`.
3. `03_calendar_upcoming.jpg`: 앞으로 다가올 공휴일·이벤트 목록과 D-Day 표기.
4. `04_cycle_calendar.jpg`: 생리 기록 기간·생리/가임기 예측을 다른 색으로 표시하는 달력과 당일 기록 패널.
5. `05_cycle_daily_log.jpg`: 생리 시작/종료, 과거 기록, 증상 선택, 기분 선택, 300자 메모. 예측은 의학적 진단이나 피임 방법이 아님.
6. `06_records_diary.jpg`: 데이트 일기 카드(대표 사진·제목·장소·날짜·사진 수), `데이트 일기 / 위시리스트 / 선물 메모` 탭, 추가 버튼.
7. `07_settings_profile.jpg`: 내 이름·상대 이름·사귄 날짜, 생체인증/화면 잠금, 생일·기념일 알림 사전 알림일 설정.
8. `08_settings_notifications.jpg`: 가족의 날 알림, 생리 예상일 알림, 잠금화면 비공개 알림, 달력에 주기 표시, 알림 시간, 홈 위젯에 표시할 일정 종류.

공통 UI: 다크 테마(블랙/차콜), 로즈 핑크·버건디 포인트, 큰 라운드 카드·칩, 하단 탭 `홈 / 달력 / 마법 / 기록 / 설정`. 실사진과 실명, 화면 속 날짜는 예시 데이터일 뿐이므로 테스트 시 가상의 이름·사진·날짜를 사용한다.

## 공유 범위와 개인정보 요구사항
- `공유`: 커플 프로필 중 합의한 항목, 연애 시작일, 기념일·공유 일정, 양쪽이 공유하기로 한 데이트 일기·위시리스트·선물 메모.
- `기본 개인`: 생리 날짜, 주기 예측, 증상, 기분, 상세 메모. 이 항목은 작성자 본인만 조회·수정하도록 설계한다. 파트너 공유는 항목별로 명시적인 Opt-in을 받기 전까지 허용하지 않는다. 건강 관련 기록·알림은 잠금화면과 홈 위젯에서 기본 숨김.
- 생리 달력은 공유 달력에서 혼합 노출하지 말고, 본인 계정에서만 볼 수 있는 비공개 오버레이로 설계한다. 화면의 '마법' 명칭을 보존하되 기능 설계 문서에는 의미를 명확히 적는다.
- 개인별 알림 설정과 디바이스 토큰은 별도 관리한다. 생체인증은 단말 로컬 잠금 기능으로 설계하고 서버 인증 및 DB 접근통제를 대신하지 않는다.
- `couple_id`만 전달하면 다른 커플의 데이터를 볼 수 있는 구조를 금지한다. Supabase RLS 및 적절한 테이블 Grants, 공유 파일의 비공개 Storage 정책을 설계하고 제3자 접근 거부 테스트를 포함한다.
- 초대 수락·두 명 정원·중복 가입 제한은 클라이언트 UI가 아닌 서버 측 트랜잭션에서 검증한다.
- Supabase secret/service_role 키는 앱에 저장하지 않는다.

## 홈 위젯 요구사항 및 현실적 제약
- iOS/Android 홈 화면에 (1) 연애 D+ 및 원하는 디데이, (2) 이번 달 일정 일부를 표시하는 달력 위젯을 만들고 싶다.
- 작은 디데이 위젯부터 PoC를 수행하고 달력 위젯은 최소 기능만 검사해라.
- 위젯이 Supabase를 지속 호출하지 않게 앱이 데이터를 가져와 위젯용 스냅샷을 갱신하는 구조를 기본으로 하라.
- 앱이 꺼져 있거나 자정이 지난 뒤의 위젯 갱신은 OS별로 제한될 수 있으므로 실제 가능한 방식, 재현 조건, 한계를 문서화해라.
- Expo의 `expo-widgets` 현재 공식 문서를 확인하고, 현재 설치 환경의 SDK/라이브러리 호환 버전, Android `enableAndroid` 설정, iOS/Android 별도 렌더링 구현 필요 여부, Expo Go 불가·개발 빌드 필요 여부를 먼저 검증해라. 지원 불가능한 기능은 임의의 코드를 만들어 '성공'이라고 보고하지 말아라.

## 첫 작업 범위: 분석과 최소 기술 검증만

### A. 현재 작업 디렉터리 조사 (기존 파일은 변경하지 말 것)
1. 프로젝트 소스/설정/빌드 파일을 확인하여 실제 기술 스택과 로컬 저장 방식을 파악한다. 원본 소스가 없는 경우 APK만으로 iOS 앱을 생성할 수 없다는 점과 가능한 자료 재사용 범위를 명확히 문서화한다.
2. 위 8개 이미지에서 확인한 기능을 `기존 화면에서 확인 / 버튼 존재만 확인 / 미확인`으로 나눠 기능 목록과 화면 전환 후보를 작성한다.
3. 현 프로젝트를 활용하는 방안과 React Native + Expo로 재구현하는 방안을 비교해 재사용 가능 영역과 리스크를 정리한다.
4. 아직 기존 Android 프로젝트를 덮어쓰거나 삭제하지 않는다.

### B. 개발환경·위젯 최소 PoC (작업 공간이 준비된 경우)
1. macOS의 Node.js, npm, Xcode, Android SDK/Emulator 설치 여부와 버전을 확인한다.
2. 기존 소스와 분리된 `spikes/widget-poc/` 또는 별도 디렉터리에 공식 `with-widgets` 예제를 기반으로 최소 Expo 프로젝트를 만든다. 기존 레포가 없다면 현재 폴더 구조와 충돌 없이 생성한다.
3. 하드코딩한 가상 날짜로 D+ 위젯, 3개 가상 일정으로 최소 달력 위젯을 만든다. 이 단계에서 Supabase 운영 프로젝트는 연결하지 않는다.
4. iOS Simulator와 Android Emulator에서 실행을 시도한다. Android 위젯 활성화 설정을 확인하고 양쪽 홈 화면에 실제 추가 가능한지 테스트한다.
5. 정적 분석/타입 검사/빌드 로그를 남기고 실제 성공, 미실행, 권한 부족, 환경 미비를 구별한다.
6. iOS 실기기 서명, Android APK 내부 배포, 유료 Apple Developer 계정 필요 시점과 무료 개발 서명의 제약을 문서화한다. 결제·실기기 등록·배포는 수행하지 않는다.

### C. 앞으로의 설계 문서만 작성 (운영 구현 금지)
1. 목표 기능의 단계별 MVP 우선순위를 정의한다: 인증·커플 연결 → 일정/기념일 공유 → 기록/사진 → 건강 기록 개인 영역 → 위젯/알림.
2. DB 초안을 제안한다: profiles, couples, couple_members, couple_invites, events, diaries, diary_photos, wishlists, gifts, cycle_records, cycle_daily_logs, notification_preferences, device_tokens. 실제 스키마는 관찰된 기능과 데이터 소유권에 맞춰 단순화/재구성 가능. 날짜 전용 값과 타임스탬프를 구별한다.
3. 각 테이블에 소유자, 공유 범위, 조회/생성/수정/삭제 권한, RLS 정책 방향을 정의한다. 특히 개인 건강 정보가 사용자 B에게 기본적으로 절대 노출되지 않도록 한다.
4. 한국 시간대(Asia/Seoul) 날짜 계산, 관계 시작일 포함 D+ 계산, 미래 일정 D-, 매년 반복/음력·한국 공휴일 처리, 알림 시간과 위젯 자정 갱신을 설계한다. 공휴일·음력은 검증 가능한 라이브러리 또는 공식 데이터의 활용 방법을 조사하고 임의로 하드코딩하지 않는다.
5. 기존 로컬 데이터가 있으면 백업/이관 가능성을 평가한다. 마이그레이션을 실행하지 않는다.
